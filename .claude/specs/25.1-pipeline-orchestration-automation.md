# Spec: Pipeline Orchestration Automation

## Roadmap description
Two new commands that walk a feature idea through planning, building, testing, and shipping automatically, pausing only when a real decision is needed.

## Overview
The Oxos Platform dev pipeline (`/capture-thoughts` → `/plan-release` →
`/create-spec` → `/implement-feature` → `/test-feature` →
`/code-review-feature` → `/ship-feature`) is currently driven one command at
a time, even when a stage finishes cleanly with nothing for the user to
weigh in on. This turns the user into a relay between commands and makes it
easy to skip a step, run steps out of order, or lose track of which release
number a follow-up command should target. This release adds two new
orchestration commands — `/autom-plan` and `/autom-dev` — that drive the
existing pipeline commands in sequence, exactly as documented, without
reimplementing their logic or guardrails. `/autom-plan` automates the
planning half (capture through release planning) and always stops before any
implementation begins. `/autom-dev` automates the build-and-ship half
(spec through ship) for exactly one explicitly selected release, auto-fixing
failing tests and review findings with a bounded retry count before pausing
to ask the user. Neither command is a new implementation of the development
methodology — they are thin orchestrators over the commands that already
exist.

## Release context
Release 1 of 1 — this is the only planned release for feature 25 (see
`.claude/features/releases/25-pipeline-orchestration-automation.md`).

**In scope for this release:**
- `/autom-plan` command: runs `/capture-thoughts` → `/plan-release`,
  presents the resulting release plan (or all releases if `/plan-release`
  produced more than one), recommends which release to build first, and
  stops. Never triggers implementation.
- `/autom-dev <feature.release>` command: runs `/create-spec` →
  `/implement-feature` → `/test-feature` → `/code-review-feature` →
  `/ship-feature` for exactly one selected release, waiting for each stage
  to finish before starting the next.
- Auto-fix behavior in `/autom-dev`: failing tests and code-review findings
  are auto-remediated and the relevant stage is re-run, capped at 3 attempts
  per stage. On the 3rd unsuccessful attempt, the run stops, summarizes the
  issue and a recommendation, and asks the user for permission to continue.
- `/autom-dev` loads its target release from the release plan file and the
  `features` DB table rather than requiring `/autom-plan` to have just run
  in the same session — a previously generated plan can be picked up later.
- Stage-level resumability: a subsequent `/autom-dev` run for the same
  release resumes from the first pipeline stage without a completed
  timestamp, rather than restarting from `/create-spec`.
- A run journal (decision memory + permission memory, kept as two distinct
  logical record types in one project-local file) recording what was
  requested, why, what was decided, and the scope of that decision
  (one-time / current-run / project-level / permanent policy).
- A structured run summary printed at the end of every `/autom-dev` run.
- A final duplication audit at the end of every `/autom-dev` run.
- Root-cause validation guidance embedded in `/autom-dev`'s auto-fix step,
  explicitly barring weaker assertions, sleeps/retries/timing hacks, or
  other test-only workarounds as a substitute for fixing the underlying
  behavior.

**Deferred to a future release (not built now):**
- `--dry-run` mode for `/autom-dev`.
- A dedicated `auto_pipeline_at`-style DB column for `/status`/roadmap
  visibility into "mid-automation" state (the run summary covers this for
  now).
- Composing a `--auto` flag into `/test-feature` / `/code-review-feature`
  themselves (tracked separately in
  `.claude/features/user-thoughts/dev-workflow-improvements/thoughts_2026-06-24_19-16.md`).

**Open questions carried into implementation (resolved below, revisit if
wrong):**
- *Does any spec with an "Open questions" section always pause the run?*
  Resolved for this release: `/autom-dev` pauses before `/implement-feature`
  only if the spec's "Open questions" section contains an item not already
  resolved by the spec's own "Release context" section (i.e. genuinely
  unresolved, not just carried-forward-and-answered). This keeps ordinary
  specs (like this one) from forcing an unnecessary pause while still
  catching real ambiguity.
- *Should `/autom-dev` stop at feature boundaries between releases of a
  multi-release feature?* Resolved for this release: yes implicitly — since
  `/autom-dev` always takes one explicit `<feature.release>` argument and
  never chains to the next release on its own, this is already the
  guardrail; no extra logic is needed.

`implemented_at`, `tested_at`, `reviewed_at`, `shipped_at`, `test_report`,
`review_report` (see `database/db.py`). `/autom-dev` reads these to
determine the last completed stage for a release and to resume correctly.

## Error handling
- **Missing or invalid feature/release argument to `/autom-dev`** — if
  `<feature.release>` is missing, malformed, or does not match an existing
  release row, stop immediately and print usage guidance; do not guess a
  target.
- **No release plan found for `/autom-dev`'s target** — if no matching file
  exists under `.claude/features/releases/`, stop and tell the user to run
  `/autom-plan` or `/plan-release` first.
- **Stage fails and is not retryable within policy** — after 3 unsuccessful
  attempts at a given stage, `/autom-dev` must stop (not silently continue
  into the next stage), print the stage, the failure, what was attempted,
  and a recommended next action, and ask for permission to continue.
- **Ambiguous or destructive action encountered mid-run** — e.g. a spec
  decision that can't be safely inferred, or any action that would require
  bypassing an existing guardrail (git push policy, ownership checks) — the
  run must pause, explain the exact decision needed, and wait for the user
  rather than guessing.
- **`/plan-release` returns multiple releases inside `/autom-plan`** — must
  never auto-select or auto-run more than the one release the user
  explicitly chooses; presenting all options and stopping is the only
  correct behavior.
- **Journal write failure** — if the run journal file cannot be written,
  log the error to the console and continue; a broken journal must not
  block the pipeline stage that is already in progress.

## Rules for implementation
Follow all rules in `CLAUDE.md`, in particular:
- **Git Push Policy** — `/autom-dev` must invoke `/ship-feature` for the
  push/PR/merge steps exactly as that command already does; it must not
  add any push logic of its own or push at any other point in the run.
- **No duplicate commands/skills/config/DB/process structures** — before
  writing `autom-plan.md` / `autom-dev.md`, re-confirm no existing
  command/skill already provides the required behavior (per the research
  already done for this spec: none do).
- Reuse the existing `features` table columns as the state store — do not
  add new columns or a new state file format for pipeline stage tracking.
- The run journal (decision/permission memory) must not persist sensitive
  information, and must not treat a single approval as blanket future
  authorization.

## Definition of done
- [ ] `/autom-plan` exists as a command (and matching skill) and, given a
  thought-file input, runs `/capture-thoughts` then `/plan-release` and
  stops without invoking `/create-spec` or any later stage.
- [ ] `/autom-plan` presents every release from a multi-release plan, with a
  recommendation of which to build first, and requires an explicit user
  selection before any `/autom-dev` run is suggested.
- [ ] `/autom-dev <feature.release>` exists as a command (and matching
  skill) and, given a spec'd-or-earlier release, runs `/create-spec` →
  `/implement-feature` → `/test-feature` → `/code-review-feature` →
  `/ship-feature` in order, waiting for each stage to complete.
- [ ] `/autom-dev` can be invoked in a fresh session against a release plan
  that was generated in an earlier, separate session (no dependency on
  `/autom-plan` having just run).
- [ ] Given a release whose `implemented_at` is already set but
  `tested_at` is not, `/autom-dev` resumes at `/test-feature` rather than
  re-running `/create-spec` or `/implement-feature`.
- [ ] A failing test or review finding is auto-remediated and the stage is
  re-run, up to 3 attempts; on the 3rd failure the run stops and prints the
  issue, what was attempted, and a recommendation, and waits for the user.
- [ ] The run journal file records at least one decision and one permission
  entry with request/reason/decision/scope during a run, and a later run
  does not re-ask a question whose recorded decision still applies.
- [ ] Every `/autom-dev` run ends with a structured summary listing stages
  completed, files changed, tests executed, review findings, and any
  bugs/improvements discovered.
- [ ] Every `/autom-dev` run performs and reports a final duplication audit
  before completion.
- [ ] No new Flask route, template, or DB table/column is introduced by
  this feature (verified by diffing `app.py`, `templates/`, and
  `database/db.py` against main).
- [ ] README.md updated if this feature adds, changes, or removes
  anything user-visible (new route, new feature area, tech stack
  change, or feature roadmap entry).
