## Decisions
<!-- Architectural/product choices made during this run. One entry per
     decision: what was asked, why, what was decided, scope. -->

- 2026-08-08: During `/autom-plan`, the release plan flagged that several
  affected tests call `conn.commit()` mid-test (not only in fixture
  setup/teardown), so a naive "wrap in one transaction, roll back at the
  end" won't fully protect those commits. This needs to be resolved during
  `/create-spec`/`/implement-feature` — either remove/replace mid-test
  commits so nothing commits until the final rollback, or use savepoints so
  mid-test commits can be reverted. Not yet resolved as of run start.

- 2026-08-08: `/create-spec` Step 3 flagged that 15.6 (Roadmap Stage
  Metrics) has no spec yet, so creating 15.8 skips over it in release
  numbering. Asked the user; decided to continue with 15.8 — 15.6 and 15.8
  are unrelated, independently-scoped releases under the same parent
  feature, and 15.8 was explicitly planned via `/autom-plan`. Scope: this
  run only; does not resolve or block 15.6.

- 2026-08-08: Dispatched an investigation agent to check whether a
  savepoint-based rollback (the release plan's tentative approach) is
  technically viable given that `database/db.py` and `database/queries.py`
  helpers (`seed_features`, `insert_expense`, `update_feature_request`,
  etc.) call `conn.commit()` internally. Confirmed: `get_db()` opens a new
  connection per call in production, but all 5 affected test files
  monkeypatch `get_db()` (in both `database.db` and `database.queries`) to
  return the same shared connection via a `_NoCloseProxy` that only no-ops
  `.close()`, not `.commit()`. So every app helper's internal `commit()`
  lands on the test's own connection. In PostgreSQL a `COMMIT` releases all
  savepoints on that transaction, so `SAVEPOINT` + `ROLLBACK TO SAVEPOINT`
  cannot survive a single `seed_features()` call — this is not hypothetical,
  it's exactly why the existing test author's docstring in
  `test_15_1-roadmap-pipeline.py` already states "Isolation is achieved by
  TRUNCATE, not rollback... a single outer rollback cannot undo their side
  effects" and rejected rollback for TRUNCATE.
  Decision: given savepoints are ruled out, asked the user to choose between
  (a) monkeypatching `conn.commit()` to a no-op for the duration of each
  test (on the same shared proxy connection already used), with a single
  real rollback at teardown, vs (b) a dedicated `TEST_DATABASE_URL`/schema.
  User chose (a) — no-op `commit()` + single final rollback. Scope:
  project-level for this release's test suite; implementation should extend
  the existing `_NoCloseProxy` pattern (already present in all 5 files) to
  also no-op `.commit()`, keeping the real rollback exclusively in fixture
  teardown.

- 2026-08-08 (incident, self-caused): After terminating the stuck backend,
  killed the now-unblocked-but-still-running pytest process mid-execution
  to force a clean re-run. This left the live `features` table truncated at
  0 rows with no reseed (the exact class of incident this release exists to
  prevent) — almost certainly because the in-flight test run's teardown
  (TRUNCATE-and-commit under the *old*, not-yet-fully-verified fixture code
  in some files, or a partial run caught mid-fixture) never got to run its
  restorative step. Immediately restored via `seed_features()` (48 of 49
  rows came back from the static seed data) and then manually re-inserted
  the one row `seed_features()` doesn't know about yet — `15.8` itself,
  since it was captured/planned/spec'd after the last `/ship-feature` seed
  regeneration — using the exact `captured_at`/`planned_at`/`spec_at`/
  `description` values already recorded earlier in this same run. Verified
  49/49 rows and `24.1`'s `test_report`/`review_report` intact afterward.
  No user data lost. Lesson for this run: do not run the live-DB test suite
  and kill background processes in the same window without re-verifying live
  table state immediately after any forced kill.

- 2026-08-08 (follow-up, corrected diagnosis): initially suspected the
  no-op-commit fixture was fundamentally incompatible with Supabase's
  pgbouncer transaction-pooling mode (port 6543) based on widespread test
  failures and severe slowness. Verified this directly by stashing the
  fixture changes and running one failing test
  (`test_get_roadmap_returns_200_unauthenticated`) against the completely

  compare failure counts against the modified-fixture run, but both runs
  were similarly, unusually slow against the live Supabase DB (a suite that
  normally takes seconds took many minutes on both code paths), pointing to
  transient environment/network conditions rather than a fixture defect.
  After the baseline run ran for 50+ minutes without finishing, asked the
  user again; they chose to stop waiting and proceed on the strength of the
  one confirmed spot-check plus the observation that slowness was symmetric
  across both fixture versions. Decision: keep the no-op-commit + single-
  rollback approach as implemented (per the earlier project-level decision);
  do not pivot to a direct/non-pooled connection string or a dedicated test
  database. Full-suite verification (including whatever fraction of the 128
  failures are pre-existing vs. newly introduced) is deferred to
  `/test-feature`, ideally run when the environment is faster. Scope:
  affects how this release's Definition of Done gets verified, not the
  chosen architecture itself.
