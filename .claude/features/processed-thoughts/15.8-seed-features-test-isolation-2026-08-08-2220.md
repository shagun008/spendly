# Processed Thought: Seed Features Test Isolation

## Problem / Goal
`seed_features()` in `database/db.py` is regenerated from the live DB on every
`/ship-feature` run. Several tests (`test_15_1-roadmap-pipeline.py`,
`test_15.4`, `test_15.5`, `test_15.7`, `test_15.2-roadmap-detail.py`)
`TRUNCATE features RESTART IDENTITY CASCADE` directly against the real
`DATABASE_URL` — there is no separate test database — and then call
`seed_features()` to reseed for test isolation. Three stacked bugs in the
`/ship-feature` regeneration script (dropped tuple fields, an INSERT
column/placeholder count mismatch, and `re.sub()` backslash-escape
corruption of multi-line report text) meant `seed_features()` could crash
outright on an empty table, and — even once "working" — could restore rows
with `test_report`, `review_report`, and `deployed_at` NULL, wiping
previously captured pipeline history for shipped features. These three
mechanical bugs were already fixed and shipped directly to `main` in commit
`cce2e1a` as an ad hoc fix, bypassing the normal pipeline. What remains is
the underlying design gap: any test that TRUNCATEs the live `features` table
can still lose `test_report` / `review_report` content written by
`/test-feature` or `/code-review-feature` after the last `/ship-feature` run
regenerated the seed snapshot, since that fresh content was never captured
into `db.py` yet. This is a narrower window than before, but the same root
cause.

## Who benefits
Anyone running the Oxos Platform test suite locally or in CI — test runs
against the live `features` table should never be able to destroy real
pipeline history (test/review report text, deployed timestamps) for
already-shipped features. Also benefits future maintainers of
`/ship-feature`'s regeneration script and of `seed_features()` itself, since
a regression test would catch this class of drift automatically.

## Success looks like
- Tests that need an empty/seeded `features` table no longer touch the live
  `DATABASE_URL` table directly (either via a dedicated test database/schema,
  or via a transaction that's rolled back at teardown instead of committed).
- A regression test exists asserting `seed_features()`'s row-tuple length
  matches the INSERT's placeholder count, and that a full TRUNCATE +
  `seed_features()` + spot-check round-trips `test_report`, `review_report`,
  and `deployed_at` for at least one known-populated feature.
- Running the existing TRUNCATE-based tests (`test_15_1-roadmap-pipeline.py`,
  `test_15.4`, `test_15.5`, `test_15.7`, `test_15.2-roadmap-detail.py`) no
  longer risks permanent loss of live pipeline history, even if a future bug
  is reintroduced into the seed-regeneration script.

## Constraints, risks, dependencies
- No separate test database currently exists — introducing one (e.g. a
  `TEST_DATABASE_URL` or dedicated Postgres schema) touches how tests are
  configured and run, and may have Supabase/infra implications.
- The transaction-rollback approach was already validated manually on
  2026-08-08 (TRUNCATE + reseed + spot-check inside a savepoint, rolled back,
  never committed) as the verification method for the mechanical fix — it
  could be promoted from a one-off verification technique into the actual
  test isolation strategy.
- `test_report` / `review_report` are large free-text blobs written directly
  to the live DB by `/test-feature` and `/code-review-feature`, outside the
  `/ship-feature` pipeline — any fix needs to account for that write path,
  not just the reseed path.
- The original incident was not recoverable after the fact (no local dump,
  not tracked in git, and Supabase PITR would require restoring the whole
  project rather than just this table) — whatever solution is chosen should
  reduce reliance on point-in-time recovery as the safety net.
- The three mechanical bugs (tuple builder, INSERT column/placeholder
  mismatch, `re.sub()` backslash corruption) are already fixed and shipped
  directly to `main` in commit `cce2e1a`, bypassing the normal pipeline —
  this release should not re-fix those, only address the remaining design
  gap.

## Implementation ideas / open questions
Three options were identified, not yet implemented:
1. **Stop letting tests TRUNCATE the real `features` table at all.** Point
   test isolation at a separate test database/schema (a `TEST_DATABASE_URL`
   or dedicated Postgres schema) so test isolation can never touch live
   pipeline history again, regardless of future bugs in `seed_features()`.
   Identified as the higher-leverage fix since it removes the blast radius
   entirely rather than patching around it.
2. **If TRUNCATE-based isolation against the live DB must stay**, wrap each
   test's TRUNCATE + reseed in a transaction that's rolled back at teardown
   instead of committed, so nothing persists past the test — this is the
   same technique already used manually to verify the mechanical fix.
3. **Add a regression test** asserting `seed_features()`'s row-tuple length
   matches the INSERT's placeholder count, and that a full TRUNCATE +
   `seed_features()` + spot-check round-trips `test_report` / `review_report`
   / `deployed_at` for at least one known-populated feature, so this class of
   drift is caught by CI before it ships again.

Open question: whether option 1 and option 3 should ship together in one
release (dedicated test DB + regression test), or whether option 2 is an
acceptable interim step if a dedicated test database is a larger lift than
this release should take on.

## Release pressure / deadlines
Not specified. The mechanical crash/corruption bugs are already fixed and
shipped (commit `cce2e1a`, 2026-08-08); this capture is for the remaining
design-gap work only, with no stated deadline.
