# Processed Thought: Live Learnings Section

## Problem / Goal
The Learnings section on the `/platform` page (built as part of feature 21,
Oxos Profile Page) is currently five static, hand-authored cards in
`templates/platform.html`, manually transcribed from CLAUDE.md's
Implementation Rules when 21.1 was built. The original 21.1 spec explicitly
called for this section to "later be driven from a database rather than
static content" — this enhancement is that follow-through. The goal is for
Learnings to automatically reflect the decisions, insights, and lessons
generated during project implementation runs, without anyone manually
maintaining the page.

## Who benefits
Anyone viewing the `/platform` page who wants visibility into accumulated
project/implementation knowledge — developers and stakeholders reviewing
what's been learned across releases, without relying on someone remembering
to update CLAUDE.md or the template by hand.

## Success looks like
- Learnings are generated/updated automatically from real implementation
  artifacts rather than hardcoded HTML.
- New learning cards appear without a manual UI/template edit.
- Historical learnings remain visible (nothing is silently dropped between
  runs).
- Each learning carries lightweight metadata: which release/implementation
  it came from, a type (one-time / current-run / project-level / permanent
  policy), an author (user, Admin, or System), a user upvote count, and an
  AI-derived "star" weight.
- Learnings are sorted with the most-endorsed (by upvotes and AI star)
  appearing first, making the section self-organizing over time.
- No confidential information (secrets, keys, credentials, or other
  sensitive implementation detail) is ever exposed in the UI.

## Constraints, risks, dependencies
- **Source-of-truth gap today**: prior to this, learnings were captured
  manually into CLAUDE.md's Implementation Rules (the source for the current
  5 static cards). The `.claude/features/automation/` folder — the proposed
  new source — was only just introduced as part of release 15.8, immediately
  before this thought was captured. It is a stepping stone 15.8 put in
  place, not a pre-existing system.
- **Coverage gap**: as of today there is exactly one run journal in that
  folder (`15.8-run.md`). This is expected, not a bug — `/autom-dev` is
  currently the *only* command that writes to `.claude/features/automation/`
  (per its Step 2). Releases built by manually chaining the individual
  commands (`/create-spec`, `/implement-feature`, etc. — which covers most
  of the roadmap's history) produced no automation artifact. A live-Learnings
  feature built on this folder will launch with very thin historical
  coverage and will only grow richer as more releases run through
  `/autom-dev`. CLAUDE.md remains the only record of pre-15.8 learnings.
- **Author attribution**: the automation journal doesn't currently record
  "who triggered this run" in a way that maps cleanly to logged-in app
  users vs. Admin vs. System — this needs definition before it can be
  extracted.
- **AI Star weighting formula is undefined**: no agreed formula yet for how
  the AI-endorsement weight is computed or how/when it's recomputed after
  each release (open question, see below).
- **Security**: extraction logic must guard against ever surfacing secrets,
  keys, credentials, or other sensitive content that might appear in a run
  journal's Decisions/Permissions notes.
- Minor unrelated cosmetic bug spotted while investigating this area: the
  Learnings wrapper div uses class `learners-cards` but `platform.css`
  defines `.learnings-cards` — the grid rule silently never applies. Not
  in scope for this enhancement's core goal, but worth a quick fix while
  touching this section.

## Implementation ideas / open questions
- Parse `.claude/features/automation/<release>-run.md` journal files
  (Decisions / Permissions / Stage Log sections) to extract candidate
  learnings.
- Each learning card should show: Implementation/Release tag (e.g. "Release
  24 - Auth Improvements"), Type tag (one-time / current-run / project-level
  / permanent policy, inferred from the journal entry), Author tag (By
  <user> / By Admin / By System), an upvote control (↑ count, incremented by
  user click), and an AI Star metric (e.g. "★ 15") representing an
  AI-computed endorsement weight.
- Open question raised by the user: how should the AI Star weight be
  computed (e.g. weighted average of some kind) and how/when should it be
  recomputed after every release? No formula decided yet — flagged for
  design work, possibly its own sub-release.
- Sort learnings descending by upvotes (and star weight) so the most
  endorsed rise to the top.
- Preserve existing card visual design (icon, category, title, body) — this
  is about changing the data source, not the visual design.
- Given the size (extraction pipeline + new metadata schema + voting UI +
  AI scoring + security filtering), this will likely need decomposition into
  multiple releases under 21.3 rather than a single one.
