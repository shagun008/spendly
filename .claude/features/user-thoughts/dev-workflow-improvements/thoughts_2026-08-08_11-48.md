# Automating the Dev Workflow Pipeline

## Problem
Right now every stage of the pipeline is a manual, separate slash command:

```
/capture-thoughts → /plan-release → /create-spec → /implement-feature
   → /test-feature → /code-review-feature → /ship-feature
```

Each command has to be typed and watched individually, even when the previous
stage finished cleanly with no issues. For a routine feature with no surprises,
this means the user is mostly acting as a relay between commands rather than
making real decisions. It also means it's easy to forget a step, run steps out
of order, or lose track of which release number a follow-up command should
target.

## Primary objective

Your task is to design and implement an automation capability that can orchestrate the project's existing development workflow commands without duplicating any existing commands, skills, project structures, configuration, or process documentation.

Create an automation workflow that allows the user to execute the project's development workflow through a small number of high-level commands instead of manually invoking each workflow command one after another.

The intended workflow is:

### Planning automation

`/capture-thoughts`
→ `/plan-release`

### Development automation

`/create-spec`
→ `/implement-feature`
→ `/test-feature`
→ `/code-review-feature`
→ `/ship-feature`

The automation must call the existing commands where appropriate and must also directly perform work when necessary. Do not recreate the detailed logic, guardrails, conventions, or processes already defined by the existing commands/skills.

## First: inspect the repository

Before creating anything:

1. Inspect the existing command files.
2. Inspect the existing skill files.
3. Inspect project documentation and development workflow documentation.
4. Inspect configuration files.
5. Inspect scripts and automation already present.
6. Inspect the database-related structure where relevant.
7. Inspect the existing testing infrastructure.
8. Inspect any existing automation/orchestration mechanisms.
9. Search for existing commands or skills that already solve part or all of this problem.
10. Identify the canonical location and structure for new skills/commands.

Reuse existing structures wherever possible.

### Critical reuse rule

Do NOT create:

* duplicate command files
* duplicate skill files
* duplicate process documentation
* duplicate configuration
* duplicate scripts
* duplicate database structures
* duplicate helper utilities
* redundant automation layers

If an existing command or skill already provides the required behavior, invoke or compose it rather than copying its implementation.

If an existing automation mechanism can be extended cleanly, extend it instead of introducing another competing mechanism.

Only create a new skill/command when there is a clear architectural need.

# Recommended automation architecture

Create two high-level automations rather than one large automation.

## Automation 1: `/autom-plan`

Purpose:

Run the discovery and planning portion of the development workflow.

Execution:

1. Execute `/capture-thoughts`.
2. Wait for its work to complete.
3. Pass its resulting context/output into `/plan-release`.
4. Wait for `/plan-release` to complete.
5. Present the resulting process thoughts and release plan to the user.
6. Do NOT automatically begin implementation.

The user should be able to review the proposed release plan before implementation begins.

### Multiple releases

`/plan-release` may produce multiple releases.

Do not automatically execute all releases.

Instead:

* preserve the complete release plan;
* identify the releases that were proposed;
* explain the scope of each release;
* recommend which release should be executed first;
* allow the user to explicitly select a release for `/autom-dev`.

The default execution unit should be **one release per automation run**.

This is intentional because session/context limits, accumulated implementation state, and the possibility of a large release make automatically executing every planned release less reliable.

---

# Automation 2: `/autom-dev`

Purpose:

Execute one explicitly selected release from the release plan from specification through shipping.

Expected workflow:

`/create-spec`
→ `/implement-feature`
→ `/test-feature`
→ `/code-review-feature`
→ `/ship-feature`

The automation must:

1. Load the selected release context.
2. Execute `/create-spec`.
3. Wait until the specification work is complete.
4. Execute `/implement-feature`.
5. Wait until implementation is complete.
6. Execute `/test-feature`.
7. Wait until testing is complete. Implement the fix for failed test cases. Wait until implementation is complete and all test case are passed.
8. Execute `/code-review-feature`.
9. Wait until review is complete. Implement the code review findings. Wait until code review finding implementation is complete.
10. Execute `/ship-feature`.
11. Wait until shipping is complete.
12. Produce a final structured run summary.

Do not start the next phase until the previous phase has completed successfully or has reached a clearly documented state that permits continuation.

# Workflow command fidelity

The existing workflow commands contain detailed processes, guardrails, conventions, and project-specific knowledge.

The automation must NOT replace those processes with a simplified interpretation.

For every stage:

* call the existing command;
* follow its documented process;
* use its guardrails;
* preserve its expected artifacts;
* preserve its validation requirements;
* perform any direct work required by the command;
* use the command's output as context for the next stage.

The automation is an orchestrator, not a replacement for the underlying development methodology.

---

# Context and state management

The automation should maintain enough state to safely continue between stages.

At minimum, track:

* automation run ID;
* selected release;
* current workflow stage;
* completed stages;
* generated artifacts;
* files changed;
* tests executed;
* review findings;
* shipping status;
* user decisions;
* permission decisions;
* errors;
* unresolved issues;
* discovered bugs;
* improvement opportunities;
* deviations from the expected workflow.

Use existing project state mechanisms wherever available.

Do not invent a new state-management system if the repository already has an appropriate mechanism.

---

# Permissions and user interruptions

During an automation run, the underlying agent may:

* ask for permissions;
* encounter an unexpected situation;
* make a mistake;
* discover an improvement opportunity;
* encounter an ambiguous implementation choice;
* need a user decision.

The automation must distinguish between:

### Safe to continue automatically

Examples:

* deterministic workflow transitions;
* running the next existing command;
* executing already-authorized project commands;
* routine validation;
* collecting output;
* recording non-blocking findings.

### Requires user input

Examples:

* destructive or irreversible action requiring approval;
* an architectural decision that cannot safely be inferred;
* conflicting requirements;
* missing information that materially changes implementation;
* a permission that cannot be automatically granted;
* a failure where continuing could corrupt project state.

When user input is required:

1. pause;
2. explain the exact decision;
3. record the question;
4. record the user's response;
5. continue from the current workflow state.

Do not repeatedly ask the same question if the same decision has already been explicitly recorded for the current project/run and remains applicable.

---

# Permission and decision memory

Create or reuse a project-local mechanism for recording recurring automation decisions only if one does not already exist.

Record:

* what was requested;
* why it was requested;
* what the user decided;
* the scope of that decision;
* whether it applies only to the current run or can be reused;
* whether it is safe to automatically reuse later.

Do NOT persist sensitive information.

Do NOT blindly treat every prior approval as a permanent approval.

The automation should distinguish:

* one-time approval;
* current-run approval;
* project-level workflow preference;
* permanent policy/configuration.

Prefer existing project configuration or documented project conventions over introducing another memory mechanism.

---

# Bugs and improvement opportunities

During every automation run, maintain a distinction between:

1. **Required work**
2. **Bugs discovered**
3. **Improvements discovered**
4. **Out-of-scope opportunities**
5. **Workflow/process problems**
6. **Automation problems**

Do not silently expand scope to address unrelated improvements.

Unless an existing project mechanism already exists, record these findings in the run summary first rather than automatically creating unrelated tickets/files.

The final summary should clearly identify findings that require follow-up.

If the project already has an issue/task/backlog mechanism, use it where appropriate rather than creating a parallel tracking structure.

---

# Failure handling

If a workflow stage fails:

1. Determine whether the failure is transient and safely retryable.
2. If safe, retry according to the existing command's conventions.
3. If not retryable, capture:

   * stage;
   * command;
   * failure;
   * attempted remediation;
   * current project state;
   * recommended next action.
4. Do not blindly continue into later stages when doing so could produce invalid or misleading results.
5. Preserve enough state to resume without restarting completed stages.
6. Ensure code is not going in cycles and to ensure that is not happening any command should only be tried 3 times. If the desired result, implementation, fix, outcomes is not achived till then, stop, summarize it for the user - issue and the recommendation and ask for user permission to continue.

---

# Completion criteria

The automation is complete only when:

* both high-level automations are implemented;
* existing workflow commands are reused;
* no redundant commands/skills/process structures were introduced;
* the planning automation stops after release planning;
* the development automation executes exactly one selected release;
* workflow stages execute sequentially;
* stage outputs are passed forward correctly;
* interruptions are handled safely;
* decisions and permissions are recorded appropriately;
* bugs and improvements are surfaced;
* failed stages are recoverable where possible;
* the implementation follows the repository's existing conventions;
* the automation itself is tested.

Before finishing, review the repository again for duplicate or redundant structures introduced by this work and remove/refactor anything unnecessary.
