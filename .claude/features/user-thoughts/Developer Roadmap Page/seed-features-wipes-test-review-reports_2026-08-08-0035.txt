# Thought: seed_features() wipes test_report / review_report / deployed_at on reseed

## The bug

Whenever a test suite (or anything else) TRUNCATEs the `features` table against
the real `DATABASE_URL` and then calls `seed_features()` to repopulate it, the
`test_report`, `review_report`, and `deployed_at` columns come back NULL for
every row — even for features that were fully tested, reviewed, and deployed
before the truncate. On the `/roadmap` page this shows up as the tested/reviewed
dots losing their double ring and no longer being clickable, because
`templates/roadmap.html` only renders a dot as clickable when
`f.test_report` / `f.review_report` is truthy for that release row.

## Root cause

`seed_features()` in `database/db.py` is auto-regenerated by `/ship-feature`
Step 9d every time a feature ships. That regeneration script selects
`test_report`, `review_report`, and `deployed_at` from the live DB and writes a
comment claiming the row tuples include them ("columns: ... test_report,
review_report, deployed_at"), but the actual generated row tuples only contain
14 fields (through `shipped_at`) — the three report/deploy fields are silently
dropped from the tuple itself.

The `INSERT INTO features (...)` statement immediately below, however, lists
all 17 columns and 16 `%s` placeholders (`shipped_at` plus
`test_report, review_report, deployed_at`), created by an earlier edit to
`ship-feature.md`'s Step 9d script that updated the SELECT and INSERT column
lists but not the per-row tuple builder (`fmt(r[...])` calls) that actually
assembles each row.

This mismatch (16 placeholders, 14-value tuples) means `seed_features()` cannot
insert a single row without immediately raising
`IndexError: tuple index out of range` from psycopg2 — confirmed live by
running it directly against the real DB. In normal `app.py` startup this never
surfaces because `seed_features()` early-returns when the table already has
rows (`if count > 0: return`). But several tests
(`test_15_1-roadmap-pipeline.py`, `test_15.4`, `test_15.5`, `test_15.7`,
`test_15.2-roadmap-detail.py`) explicitly `TRUNCATE features RESTART IDENTITY
CASCADE` against the real `DATABASE_URL` (there is no separate test database)
and then call `seed_features()` to reseed it for test isolation. With the
table empty, the guard no longer protects the broken INSERT, so the call
should be crashing during those test runs too — worth confirming during the
fix whether tests are catching/swallowing that exception (e.g. via a broad
`except`) or whether a different code path is doing the actual reseed.

Separately — even once the column/placeholder counts are made consistent —
`seed_features()` as designed can only ever restore what Step 9d captured into
`db.py` at the time of the last `/ship-feature` run. `test_report` and
`review_report` are large free-text blobs written directly to the DB by
`/test-feature` and `/code-review-feature` outside the ship pipeline; if they
change after the last ship (or a test/review reran without a subsequent ship),
a truncate+reseed will roll them back to a stale or absent snapshot, not the
current live value. So this is really two problems stacked: (1) a mechanical
bug making every reseed crash/wipe those columns entirely, and (2) a design
gap where TRUNCATE-based test isolation against the live table is inherently
lossy for any column that isn't fully captured in the last committed seed
snapshot.

## Confirmed impact

Reproduced live on 2026-08-08: truncating `features` and calling
`seed_features()` raised `IndexError` and left the table at 0 rows. Restoring
from the (buggy, 14-field) seed data brought back all 46 rows but with
`test_report`, `review_report`, and `deployed_at` NULL on every single row —
including features that had genuinely shipped, been tested, and been
reviewed. That report text was not recoverable (no local dump, not tracked in
git, and Supabase PITR would require restoring the whole project to a past
point rather than just this table).

## Possible solution

1. Fix Step 9d's row-tuple builder in `.claude/commands/ship-feature.md` (and
   regenerate `database/db.py` once) so each tuple actually includes
   `test_report`, `review_report`, and `deployed_at`, matching the INSERT's
   column list and placeholder count. This alone fixes the crash and makes
   `seed_features()` at least round-trip whatever was true as of the last ship.
2. Stop letting tests TRUNCATE the real `features` table at all. Point test
   isolation at a separate test database/schema (a `TEST_DATABASE_URL`, or a
   dedicated Postgres schema/savepoint per test) so a broken or lossy
   `seed_features()` can never touch live pipeline history again. This is the
   higher-leverage fix — it removes the blast radius entirely regardless of
   what bugs seed_features() has in the future.
3. If real TRUNCATE-based isolation against the live DB must stay for some
   tests, wrap each test's TRUNCATE + reseed in a transaction that's rolled
   back at teardown instead of committed, so nothing persists past the test.
4. Add a regression test that asserts `seed_features()`'s row-tuple length
   matches the INSERT's placeholder count (or better, that a full
   TRUNCATE + `seed_features()` + spot-check round-trips test_report/
   review_report/deployed_at for at least one known-populated feature) so this
   class of drift is caught before it ships again.
