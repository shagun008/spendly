# Thought: seed_features() wipes test_report / review_report / deployed_at on reseed

## Status: partially resolved (2026-08-08)

The mechanical crash/corruption bugs described below are fixed and shipped
directly to `main` in commit `cce2e1a` (bypassed the normal pipeline — this
was an ad hoc fix, not a spec'd feature). The underlying design gap that
caused the symptom in the first place is still open — see "Remaining work"
at the bottom. That part still needs to go through the normal pipeline
(`/capture-thoughts` → `/plan-release` → ... → `/ship-feature`).

## The bug (as originally reported)

Whenever a test suite (or anything else) TRUNCATEs the `features` table against
the real `DATABASE_URL` and then calls `seed_features()` to repopulate it, the
`test_report`, `review_report`, and `deployed_at` columns come back NULL for
every row — even for features that were fully tested, reviewed, and deployed
before the truncate. On the `/roadmap` page this shows up as the tested/reviewed
dots losing their double ring and no longer being clickable, because
`templates/roadmap.html` only renders a dot as clickable when
`f.test_report` / `f.review_report` is truthy for that release row.

## Root cause — three stacked bugs, all fixed

Investigation turned up three independent bugs in `/ship-feature`'s Step 9d
regeneration script (`.claude/commands/ship-feature.md`), which regenerates
`seed_features()` in `database/db.py` from the live DB on every ship:

1. **Tuple builder dropped three fields.** The script's SELECT and INSERT
   column lists included `test_report`, `review_report`, `deployed_at`, but
   the per-row tuple builder (`vals = [...]`) never appended `fmt(r['test_report'])`
   etc. — so every generated row tuple silently had 3 fewer values than the
   INSERT expected. **Fixed**: tuple builder now includes all three fields.

2. **INSERT column/placeholder count mismatch.** Separately, the INSERT
   statement listed 17 column names but only 16 `%s` placeholders (off by
   one). This alone would have thrown `TypeError: not all arguments converted
   during string formatting` even after fixing bug 1. **Fixed**: now 17
   placeholders for 17 columns.

3. **`re.sub()` backslash-escape corruption.** The script splices the
   generated function body into `db.py` via `re.sub(pattern, new_body_string,
   source)`. Python's `re.sub` interprets backslash escapes (e.g. `\n`) in
   the *replacement string* argument — so any report text containing embedded
   newlines had its escaped `\n` sequences silently converted into real
   newlines, breaking the generated file's Python syntax entirely. This bug
   only manifests once `test_report`/`review_report` actually contain
   multi-line text, which is likely why it went unnoticed until now. **Fixed**:
   replacement is now a `lambda m: new_body_final` function, which bypasses
   backslash interpretation.

Combined, bugs 1+2 meant `seed_features()` could not insert a single row
without crashing (`IndexError` / `TypeError`) once the table was actually
empty. In normal `app.py` startup this never surfaced because
`seed_features()` early-returns when the table already has rows. But several
tests (`test_15_1-roadmap-pipeline.py`, `test_15.4`, `test_15.5`, `test_15.7`,
`test_15.2-roadmap-detail.py`) explicitly `TRUNCATE features RESTART IDENTITY
CASCADE` against the real `DATABASE_URL` (there is no separate test database)
and then call `seed_features()` to reseed it for test isolation — that's
where the empty-table path, and therefore the crash, was actually hit.

## Confirmed impact (before the fix)

Reproduced live on 2026-08-08: truncating `features` and calling
`seed_features()` raised `IndexError` and left the table at 0 rows. Restoring
from the (buggy, 14-field) seed data brought back all 46 rows but with
`test_report`, `review_report`, and `deployed_at` NULL on every single row —
including features that had genuinely shipped, been tested, and been
reviewed. That report text was not recoverable (no local dump, not tracked in
git, and Supabase PITR would require restoring the whole project to a past
point rather than just this table).

## Verification (after the fix)

All three fixes verified with a rollback-only transaction against the live
DB (TRUNCATE + reseed + spot-check inside a savepoint, then rolled back —
never committed): all 46 rows round-tripped correctly, `test_report` and
`review_report` content matched for feature `24.1`, and the live table was
confirmed unchanged (still 46 rows) after rollback. `ast.parse()` and `black
--check` both confirm the regenerated `database/db.py` is valid.

## Remaining work — not yet done

The three bugs above only made `seed_features()` correctly restore whatever
was captured into `db.py` **as of the last `/ship-feature` run**. They do not
fix the actual design gap that caused the symptom:

`test_report` and `review_report` are large free-text blobs written directly
to the live DB by `/test-feature` and `/code-review-feature`, outside the
ship pipeline. If a test truncates the live `features` table *after* those
commands ran but *before* the next `/ship-feature` regenerates the seed
snapshot, that fresh report content is still lost on reseed — same symptom,
same root cause, just a narrower window. This will keep happening for any
feature whose test/review reports haven't yet been captured by a
`/ship-feature` run when one of the 5 TRUNCATE-ing tests fires.

Possible solutions, not yet implemented:

1. **Stop letting tests TRUNCATE the real `features` table at all.** Point
   test isolation at a separate test database/schema (a `TEST_DATABASE_URL`,
   or a dedicated Postgres schema) so test isolation can never touch live
   pipeline history again, regardless of what bugs `seed_features()` has in
   the future. This is the higher-leverage fix — it removes the blast radius
   entirely rather than patching around it.
2. **If TRUNCATE-based isolation against the live DB must stay**, wrap each
   test's TRUNCATE + reseed in a transaction that's rolled back at teardown
   instead of committed, so nothing persists past the test (this is exactly
   the technique used to verify the fix above — it could become the actual
   test isolation strategy, not just a one-off verification method).
3. **Add a regression test** that asserts `seed_features()`'s row-tuple
   length matches the INSERT's placeholder count, and that a full
   TRUNCATE + `seed_features()` + spot-check round-trips test_report /
   review_report / deployed_at for at least one known-populated feature — so
   this class of drift is caught by CI before it ships again, rather than
   discovered by hand.
