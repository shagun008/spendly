# Release Plan: Seed Features Test Isolation

## Roadmap description
Tests that reset the pipeline history table can no longer wipe real feature test and review records.

## Summary
This release closes the remaining design gap behind the `seed_features()` data-loss incident from 2026-08-08. The three mechanical bugs (tuple builder, INSERT column/placeholder mismatch, `re.sub()` backslash corruption) were already fixed and shipped directly to `main` in commit `cce2e1a`. What's left is that five test files (`test_15_1-roadmap-pipeline.py`, `test_15.4-release-type-classification.py`, `test_15.5-release-notes-modal.py`, `test_15.7-grouping-foundational-features.py`, `test_15.2-roadmap-detail.py`) `TRUNCATE features RESTART IDENTITY CASCADE` directly against the live `DATABASE_URL` — there is no separate test database — meaning any future regression in `seed_features()` (or any other bug) could again destroy `test_report` / `review_report` / `deployed_at` history for already-shipped features. This is a single release: convert those five files' isolation strategy from commit-based TRUNCATE to transaction-rollback-based isolation, and add a regression test that guards `seed_features()`'s row/column parity and round-trip fidelity going forward, built on the same safe isolation mechanism so it can't itself corrupt live data.

## Releases

### Release 1 — Transaction-Rollback Test Isolation + Regression Guard (MVP)
- **Scope:**
  - Convert the shared TRUNCATE-based fixtures in the five affected test files to wrap their setup/teardown in a transaction rolled back at the end of each test, instead of `TRUNCATE` + `commit()`. This includes auditing and updating any mid-test `conn.commit()` calls (e.g. `_insert_feature_row`, `_truncate_features`, `auth_client`'s user insert in `test_15_1-roadmap-pipeline.py`) that currently commit outside the fixture's own setup/teardown, since a wrapping rollback only protects data that hasn't been separately committed.
  - Add a new regression test asserting that `seed_features()`'s per-row tuple length matches the INSERT statement's placeholder count (guards against bug classes 1 and 2 from the original incident).
  - Add a round-trip regression test: TRUNCATE (within a rolled-back transaction) + `seed_features()` + spot-check that `test_report`, `review_report`, and `deployed_at` for at least one known-populated feature match the values in `database/db.py`'s seed data.
  - No production code changes — `seed_features()` and the `/ship-feature` regeneration script are unchanged in this release; the mechanical bugs are already fixed in `cce2e1a`.
- **Spec slug:** seed-features-test-isolation
- **Spec arg:** `15.8 seed-features-test-isolation`
- **Depends on:** nothing (commit `cce2e1a` already shipped independently)
- **Risk:** medium — touches shared fixture/teardown logic across five existing test files; incorrect rollback wiring could mask real test failures, leave transactions open across tests, or reintroduce commit-based side effects if a mid-test commit is missed

## Deferred / Out of scope
- **Dedicated `TEST_DATABASE_URL` / Postgres schema for test isolation** — identified as the higher-leverage fix (removes the blast radius entirely, protects against future `seed_features()` bugs regardless of isolation technique) but requires new env config, provisioning, and possibly CI changes. Not pursued in this release per explicit choice to keep scope to the lower-lift transaction-rollback approach.

## Open questions
- The existing test fixtures (particularly in `test_15_1-roadmap-pipeline.py`) call `conn.commit()` at multiple points mid-test — not only in fixture setup/teardown (e.g. `_insert_feature_row`, `auth_client`'s throwaway user insert). A pure "wrap the whole test in one transaction, roll back at teardown" approach only protects data that isn't separately committed along the way. Implementation will need to either: (a) remove/replace those mid-test `commit()` calls so nothing commits until the final rollback, or (b) use savepoints so mid-test commits can still be reverted. This should be resolved during `/create-spec` or `/implement-feature`, not left ambiguous in code.
- Confirm whether `pytest-flask`'s test client interacts with the DB connection in a way that's compatible with a long-lived uncommitted transaction spanning the whole test (the existing `_NoCloseProxy` pattern suggests connection reuse across the fixture is already accounted for, but should be re-verified against the rollback approach specifically).
