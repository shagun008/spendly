# Release Plan: Live Learnings Section

## Roadmap description
The Learnings section on the Oxos Platform page now grows automatically from real project history instead of a fixed list.

## Summary
The Learnings section on the `/platform` page currently displays five hardcoded cards manually transcribed from CLAUDE.md. This feature evolves it into a live section driven by `.claude/features/automation/` run journals — the per-release Decisions/Permissions/Stage Log artifacts introduced by 15.8. The work is decomposed into three releases: Release 1 builds the extraction pipeline and DB-backed rendering (MVP, replacing the static cards); Release 2 adds user upvoting and sorts by endorsement; Release 3 adds an AI-computed "star" weight once the scoring formula is defined. Author attribution starts as "System" in Release 1 and can be upgraded to real per-user attribution later if the automation journals begin recording who triggered each run.

## Releases

### Release 1 — Live Learnings from Automation Journals (MVP)
- **Scope:** New `learnings` DB table. A parser reads `.claude/features/automation/*.md` run journals (Decisions/Permissions/Stage Log sections) and upserts extracted learnings, each tagged with its originating release number/title and a type (one-time / current-run / project-level / permanent policy) inferred from context. The `/platform` route queries this table and renders learnings dynamically, replacing the 5 hardcoded cards, while preserving the existing card visual design (icon, category, title, body). Extraction excludes anything resembling a secret/key/credential. Also fixes the pre-existing `learners-cards` / `.learnings-cards` CSS class mismatch in this template. Author tag shows "System" for all rows in this release (no per-user attribution exists in journals yet).
- **Spec slug:** live-learnings-automation-extraction
- **Spec arg:** `21.3.1 live-learnings-automation-extraction`
- **Depends on:** nothing (21.1/21.2 already shipped; the automation folder already exists from 15.8)
- **Risk:** medium — the extraction heuristic (turning free-text journal prose into discrete titled cards) is the least-defined part of this release. Historical coverage will be thin at launch (only `15.8-run.md` exists today) but the page must render correctly with 1 learning or 100.

### Release 2 — Upvoting
- **Scope:** Adds an upvote count to each learning, a POST route for a logged-in user to increment a learning's upvote count, an up-arrow UI control on each card, and sorts learnings descending by upvote count. If/when automation journals begin recording who triggered a run, real per-user author attribution can replace the "System" placeholder here.
- **Spec slug:** live-learnings-upvoting
- **Spec arg:** `21.3.2 live-learnings-upvoting`
- **Depends on:** Release 1
- **Risk:** low — additive; does not change the extraction pipeline.

### Release 3 — AI Endorsement Star
- **Scope:** Defines and implements the AI-star scoring formula, computes/recomputes it after each `/autom-dev` run, displays it on each card, and extends sorting to weigh upvotes and star together.
- **Spec slug:** live-learnings-ai-star
- **Spec arg:** `21.3.3 live-learnings-ai-star`
- **Depends on:** Release 1 (and ideally Release 2, since the final sort blends both signals)
- **Risk:** high — the scoring formula is explicitly undecided; this release cannot be spec'd until that open question is resolved.

## Deferred / Out of scope
- Making `/autom-dev` (or an equivalent journal-writer) run for every pipeline path, so that manually-chained-command releases also produce automation artifacts. Right now only `/autom-dev`-orchestrated releases get a journal at all, so most historical releases will never surface as learnings. This is a pipeline-tooling change outside this feature's scope.

## Open questions
- What is the actual AI-star weighting formula, and how/when does it recompute after each release? (blocks Release 3)
- How should "author" be derived once it's not just "System" — is there a reliable way to capture which logged-in user triggered a dev-workflow run today, or does that require its own tooling change first?
